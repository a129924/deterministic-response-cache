# deterministic-response-cache agent guidance

## Baseline guardrails

- agent 的回覆、文件與規劃內容優先使用繁體中文；既有的技術名稱、檔名與必要術語可維持英文。
- 這是全新的 repository；不得引用、遷移、重構或相容任何舊 gateway 的設計、API、模組或工作流程。
- 開始任何實作前，必須先有該能力專屬、已確認的 topic plan；不得從 baseline 直接推導實作細節。
- Identity BC 是模型身分與完整請求身分的唯一 authority。其他 boundary 不得建立、推測或重新解讀 identity 規則。
- CacheStore 僅是 Response Reuse BC 的內部保存元件；它不得成為頂層 BC，也不得管理 identity、runtime 或模型執行。
- Loaded Runtime Cache、Model Execution 與 Provider Adapter 都必須各自以獨立 topic 規劃與實作；不得由 Response Reuse topic 提前引入。
- 架構責任、邊界與演進順序以 `docs/` 文件及 `docs/architecture/business-capability/index.html` 的 BC 圖為準；若實作提案與其衝突，先更新並確認架構文件，再開始實作。

## Observer / Dispatcher Governance

- Observer / Dispatcher 是 repository 頂層的唯讀協調者：只可盤點 state、派遣一個專責角色、彙整 bounded result，並回報 `可直接前進`、`needs-rework`、`blocked` 或 `human-check`。
- 只有 Planner 可對**單一 topic**執行 preflight，並從該 topic 已提交且明確宣告為 approved 的 candidate evidence 判定 candidate、phase、gate 與 next role。未提交、隱含、過期或 `needs-rework` evidence 一律不是 routing authority；Observer 不得自行選擇 active topic、手算或推測 gate，或重新解讀 locked decisions。
- 每個 topic 的 routing evidence 僅限其已提交的 topic plan、required step tracker、該 route 要求的 approved Plan-Reviewer receipt、immutable subject SHA、Tester evidence 與 independent Reviewer evidence；它們不得跨 topic 重用。不得以 chat、branch、summary、`GOAL.md` 或 `.github/agents/**` 補推、選擇或替代 evidence。
- runtime bootstrap 的唯一入口是 Planner，且每個 topic 只可發生一次。其後 Planner 的 runtime allowlist 只有 `Plan-Creator`、`Plan-Reviewer`、`Implementer`、`Tester`、`Reviewer`、`Explorer`；Observer 只能在 Planner 對該 topic 的 candidate、phase、gate 與 next role 作出明確判定後，從此 allowlist 派遣一個角色。不得以 Planner 作 next role、自我派遣、在同一 topic 平行扮演多個角色，或擴增角色集合。
- 角色必須在同一 topic 真實分離：Plan-Creator author plan，Plan-Reviewer 獨立審核 planning evidence，Implementer 實作，Tester 驗證，Reviewer 只做 independent implementation verification 與已通過該 topic Q gate 後的 PR comment classification / routing；Planner 依 gate 判定後續角色。`Reviewer` 不是 Human reviewer，無權給 PR approval、要求/接受 review、merge 或代表 Human 關閉 workflow。不得以隱藏 chat context 或同一角色宣稱多重 gate 已完成。
- 缺少該 topic required evidence、同一 topic state 或 scope 矛盾時，回報 `blocked`；同一 topic 有多 candidate 或 plan 與 step 指向不同 topic 時，回報 `human-check`。不同 topic 的 declared path 重疊、candidate/evidence/subject 指向衝突，或 branch/worktree 不隔離時，一律回報 `human-check`。Plan-Creator 不得 refine、選擇或 self-close candidate。
- Observer 不得實作或改檔，不得執行 git、commit、push、PR、merge、release、tagging 或 post-merge，不得處理 review comments，也不得自行宣告 approval、human check 或 workflow gate 完成。
- `.github/agents/**` 是 frozen provenance：不得修改，且不得作為 runtime 或 routing dependency。
- Tester 是每個 topic 的 implementation 與 independent Reviewer 之間必要的獨立 phase：Tester 只寫入該 immutable subject 的 factual evidence，Reviewer 只能使用同一 topic、同一 subject 的 passing Tester evidence 審核。Q gate 的 Reviewer evidence 最多建立該 topic 的 active-candidate close record，絕不等同 merge approval。
- `workflow-concurrency-supersession` 的 executable validation-evidence contract 固定為：Tester 唯一可寫入 `plan/workflow-concurrency-supersession/workflow-concurrency-supersession.tester-evidence.json`；其 JSON object top-level keys 必須恰為 `schema_version`、`topic`、`implementation_subject_commit`、`status`、`commands`、`recorded_by`，其中 `schema_version` 必為 integer `1`、`topic` 必為 `workflow-concurrency-supersession`、`implementation_subject_commit` 必為四檔 immutable implementation subject commit 的完整 40-hex SHA、`status` 必為 `passing|failing`、`commands` 必為至少一項 object 的 non-empty array，且每項只含 non-empty string `command` 與 integer `exit_code`、`recorded_by` 必為 `Tester`；只有所有 commands 的 `exit_code` 都是 `0` 時才可寫 `status: "passing"`，`failing` 必須至少有一個 non-zero exit code。Tester 完成後，僅 Implementer 可先以 sole evidence-only commit 提交原樣 Tester evidence。Independent Reviewer 唯一可寫入 `plan/workflow-concurrency-supersession/workflow-concurrency-supersession.implementation-review-log.json`；其 JSON object top-level keys 必須恰為 `schema_version`、`topic`、`implementation_subject_commit`、`tester_evidence_commit`、`verdict`、`blocking_issues`、`recorded_by`，其中 `schema_version` 必為 integer `1`、`topic` 必為 `workflow-concurrency-supersession`、`implementation_subject_commit` 必為同一完整 40-hex SHA、`tester_evidence_commit` 必為單獨提交且只含 passing Tester evidence 的完整 40-hex SHA、`verdict` 必為 `approved|needs-rework`、`blocking_issues` 必為 string array，且 `approved` 時為空、`needs-rework` 時至少一項、`recorded_by` 必為 `Independent Reviewer`。Reviewer 只可消費已提交、同 topic、同 subject 且 `status: "passing"` 的 Tester evidence，否則 fail closed 且不得產生 review evidence；之後僅 Implementer 可再以 sole evidence-only commit 提交原樣 Reviewer evidence。
- 本 topic 的固定順序為：(1) Implementer 對且只對 `AGENTS.md`、`plan/agent-handoff-workflow.md`、`plan/topic-plan-contract.md`、`tests/test_observer_dispatcher_governance_contract.py` 建立 immutable implementation subject commit；(2) Tester 寫 Tester evidence，但不 commit；(3) 獨立 Implementer 原樣以 sole evidence-only commit 提交 Tester evidence；(4) Independent Reviewer 消費該 committed passing evidence 後寫 Reviewer evidence，但不 commit；(5) 獨立 Implementer 原樣以 sole evidence-only commit 提交 Reviewer evidence。兩份 evidence 都不得與 implementation、planning artifact 或另一份 evidence 共用 commit；僅 `approved` 可進入 Planner Phase 4.5，`needs-rework` 只可回到 Implementer，並以新的 implementation subject 重複完整 sequence。本次四檔 binding 是唯一一次 `workflow-concurrency-supersession` transition-only test repair；它只授權此測試檔，絕不授權其他 topic 或未來 subject 擴張。B6R13/R23 是 `observer-dispatcher-governance` 的 subject-local obligation，不是其他 topic 的全域前置條件。
- 對尚無任何 topic artifacts 的新 topic，Human 只提供符合 `^[a-z][a-z0-9]*(?:-[a-z0-9]+)*$` 的 slug 與 non-empty intent。Planner 以 read-only admission preflight 確認 local `dev` 為完整 40-hex base SHA、五個 initial artifacts 在該 base 與工作樹都不存在、`topic/<slug>` 與 `<repo-parent>/worktrees/<slug>` 都不存在，且沒有 active topic 的 declared path（相同、祖先或子孫）或 topic identity conflict；任一失敗一律 `human-check`。只有通過後，admission-only Implementer 可執行等價於 `git worktree add -b topic/<slug> <repo-parent>/worktrees/<slug> <dev-base-SHA>` 的隔離 setup，不得寫 tracked files 或 commit；Planner 驗證 branch、HEAD full SHA 與 clean tracked status 後，才派 Plan-Creator 在該 worktree 寫入且只寫入 `analysis/<slug>/requirements.md`、`analysis/<slug>/technical-spec.md`、`plan/<slug>/<slug>.plan.md`、`plan/<slug>/<slug>.spec.md`、`plan/<slug>/<slug>.step.md`，再依正常 committed Plan-Reviewer sequence。`dev` 是 integration baseline，不承載並行 active topic writer；此 universal admission 不擴張本 topic 的 transition-only test repair，亦不授權任何 implementation path。
- 互不衝突的 topic 可在隔離的 branch/worktree 並行推進至 independent Reviewer。每個 topic 僅能在其 required evidence、Tester evidence、independent Reviewer approval、Planner Phase 4.5 alignment 與既有 human authorization 均具備時，由 Implementer 對已列 scope 執行 bounded commit、push 與 draft PR。每個 publish-in-progress 只能轉為自己的 `pr-open`；可同時存在多個 draft PR。`pr-open` 後 Human 可進行 PR review，且只有 Human 可 merge、release、post-merge、tag 與建立 final summary。
- B6R13/R23 保留為 `observer-dispatcher-governance` topic 的 subject-local unresolved obligation：其 route 仍是 `B6R13 -> R23 -> S17 -> T17 -> V17 -> Q17 -> thread-classification -> comment-resolve -> human-check`，state 是 `R23_REVIEW_PENDING`。它不作其他 topic 的全域前置條件，且不得補建、取消或以聊天結果視作完成。B6R12/R22/S16-Q16、B6R10/R20 與更早 records 均 frozen nonrouting provenance。R23 只可記 committed B6R13 的 post-commit facts；B6R13/R23 的 commit、tree、blob、HEAD 與 outcome 不得預填。
- S17 only modifies its declared exact fourteen paths. It preserves direct imports and must not introduce `importlib`、`__import__` 或 `sys.modules` substitution. T17/V17/Q17 use new B6R13 evidence paths; Q17 is an actual committed full-SHA triple gate that authorizes classification only, never comment resolution, PR approval or merge. Only a subsequent independent classification can identify individual threads as addressed-and-resolvable; only an Implementer may then leave the declared bounded reply and resolve that exact thread.

## Test Preservation

- 必須保留既有測試的 direct import、fixture、mock 與 assertion 行為。不得以 `importlib`、`__import__` 或 `sys.modules` 的動態載入取代 direct-import regression。
- 只有已核准 topic 明定「import 行為本身」為被測需求時，才可新增專用 import-behavior test；它不得取代既有的 direct-import regression test。
